AdvLab 표준 설계·기획 문서 13종 - 프롬프트로 완성하는 워크북

이 책은 여러분의 아이디어를 실제 제품 수준의 기획·설계 문서 13종으로 만드는 과정을, 복사 → 붙여넣기 → 실행 프롬프트로 따라오는 실습서입니다. 각 문서가 무엇인지 먼저 이해하고, 프롬프트를 생성형 AI(Claude Code)에 붙여넣어 문서를 생성한 뒤, 점검 포인트로 확인합니다.

사용 규칙 3가지 1. 프롬프트 카드 우측 상단의 복사 버튼을 눌러 그대로 붙여넣습니다. 2. 시작 전에 여러분의 아이디어를 파일 하나에 적어, 생성형 AI 프롬프트에 첨부합니다(아래 P0-6 · 아이디어 파일 준비하기 참고). 이후 프롬프트는 그 아이디어 파일을 근거로 문서를 만듭니다. 3. 카드는 위에서 아래로. 다음 문서는 앞 문서를 근거로 만들어 서로 어긋나지 않게 합니다.

Part 0 · 준비하기

P0-1 · "표준 문서 세트"란? (13종 지도)

제품을 만들 때는 코드보다 먼저 "무엇을·왜·어떻게" 만들지 적은 문서가 필요합니다. 실무에서는 어떤 제품이든 똑같은 13종 문서 틀(Adv 표준)을 쓰도록 정해 둡니다 - 사람이 바뀌거나 제품이 늘어도 문서가 들쑥날쑥하지 않게 하기 위해서입니다.

P0-2 · 좋은 프롬프트의 4요소 (원리 카드)

프롬프트가 막힐 때는 아래 4가지가 들어갔는지 확인하세요.

  1. 무엇을 - 하고 싶은 일(목표)
  2. 무엇을 근거로 - 참고할 문서·폴더(맥락)
  3. 어떻게 - 형식·제약(목차대로, 표로, 쉬운 말로 …)
  4. 결과물 - 어디에 어떤 형태로 저장할지

만능 템플릿

[하고 싶은 일]을 해줘.
[이 문서 / 이 폴더]를 근거로, [목차·형식·제약]으로 만들고,
결과는 docs/design/[번호_문서명].md 로 저장해줘.

P0-3 · 문서 폴더 만들기

언제 작업 폴더를 정하고 Claude Code를 연 직후

이 프로젝트의 설계 문서를 만들 폴더를 준비해줘.
 - docs/design/  : 표준 기획·설계 문서 13종을 넣을 곳
 - mockup/       : 화면 목업(HTML 시안)을 넣을 곳
앞으로의 작업 규칙을 담을 CLAUDE.md 도 만들어줘.
문서는 모두 한국어로, 파일명은 "번호_문서명.md" 형식으로 저장할 거야.

기대 산출물 docs/design/ · mockup/ 폴더 + CLAUDE.md 점검 포인트 폴더와 파일이 생겼는가

P0-4 · CLAUDE.md에 문서 규칙 적기

언제 폴더를 만든 직후 (앞으로 이 규칙을 지킵니다)

이 프로젝트 CLAUDE.md 에 문서 작성 규칙을 적어줘.
 ① 모든 문서는 한국어로 쓴다.
 ② 설계 문서는 docs/design/ 에 "번호_문서명.md" 로 저장한다.
 ③ 각 문서 맨 위에 메타 표(작성일·버전·작성방식)를 넣는다.
 ④ 각 문서 맨 아래에 변경이력 표(일자·버전·변경내용)를 넣는다.
 ⑤ 비전공자도 이해할 수 있게 쉬운 말로 쓴다.

기대 산출물 규칙이 담긴 CLAUDE.md 점검 포인트 규칙 5개가 적혔는가

P0-5 · 표준 문서 정의 이식하기 (점검 기준 심기)

언제 폴더를 만든 직후, 문서 작성을 시작하기 전 (한 번만)

"이 문서가 표준 목차를 다 채웠는지 점검해줘" 같은 요청이 제대로 되려면, AI가 참고할 표준 문서 정의가 프로젝트 안에 있어야 합니다. 함께 받은 Adv_문서정의_13종.md(문서 13종의 목록·필수 목차·점검 기준)를 프로젝트로 한 번만 이식하세요. 경로 부분만 본인 것으로 바꿔 붙여넣으면 됩니다.

함께 받은 "표준 문서 정의" 파일을 지금 이 프로젝트에 이식해줘.
정의 파일 경로: <받은 폴더 경로>/Adv_문서정의_13종.md
해줄 일:
1. 그 파일을 docs/design/_문서정의_13종.md 로 복사해줘(기존 파일은 덮어쓰지 말고 새로 추가만).
2. 앞으로 문서를 만들고 점검할 때, 이 파일의 "목차·규칙·점검 기준"을 근거로 삼겠다고 확인해줘.

기대 산출물 docs/design/_문서정의_13종.md 점검 포인트 정의 파일이 프로젝트 안에 복사됐는가 💡 팁 파일 첨부가 되는 환경이면, 이식 없이 프롬프트에 Adv_문서정의_13종.md 를 직접 첨부해도 됩니다.

P0-6 · 아이디어 파일 준비하기 (첨부용)

문서 만들기의 출발점은 여러분의 아이디어입니다. 아래 틀로 아이디어를 파일 하나에 적어 저장하세요(예: idea.md). 그런 다음 생성형 AI(Claude Code)에 그 파일을 첨부하거나, 프로젝트 폴더에 두고 경로로 가리키면 됩니다.

아이디어 파일 틀 (복사해서 내용만 채우세요)

파일 이름: idea.md

# 내 아이디어
- 무엇: (무엇을 하는 서비스인지 한 줄로)
- 누구를 위해: (주요 사용자)
- 왜: (어떤 불편을 해결하나)
- 하고 싶은 기능: (3~5개, 줄마다 하나씩)
- 이번엔 안 할 것: (이번 범위 밖)

💡 팁 잘 모르겠는 칸은 비워 두어도 됩니다. 다음 카드에서 AI가 되물어 채워 줍니다.

P0-7 · 아이디어를 정식 범위로 정리

언제 아이디어 파일을 첨부(또는 저장)한 뒤

첨부한 아이디어 파일(없으면 docs/design/idea.md)을 근거로,
이 아이디어를 "누가·왜·무엇을 하는 서비스"인지 3~4문장으로 정리하고,
핵심 기능 3~5개와 이번에는 하지 않을 것(범위 밖)을 구분해서
docs/design/idea_scope.md 로 저장해줘.

기대 산출물 docs/design/idea_scope.md 점검 포인트 대상·목적·핵심 활동이 또렷한가 / "할 것"과 "안 할 것"이 나뉘었는가 💡 팁 흐릿하면 → "부족한 부분을 나에게 한 번에 하나씩 물어봐 줘" 로 문답하며 채웁니다.

자주 쓰는 프롬프트 (문서마다 재사용)

R-1 · 부분만 고치기

언제 한 번에 완벽하지 않을 때. 조금씩 다듬습니다

R-3 · 표준 목차대로 됐는지 점검

R-4 · 다음 문서는 "앞 문서를 근거로"

다음 문서를 만들 때는 항상 "앞 문서를 근거로"라고 알려주세요. 그래야 문서끼리 어긋나지 않습니다. 공통 틀은 이렇습니다.

docs/design/[앞 문서] 를 근거로 [다음 문서] 를 작성해줘.
아래 목차를 채워 docs/design/[번호_문서명].md 로 저장하고, 쉬운 말로 써줘.

Part 1 · 기획서 (02)

기획서란?

무엇 제품의 목적·대상·범위·핵심개념을 못박는 "출발점 문서". 이후 모든 문서의 기준이 됩니다.

필수 목차 배경·목적 / 대상·사용자 / 범위(할 것·안 할 것) / 핵심개념(도메인) / 시스템 구성 개요 / 마일스톤 / 가정·제약

P1 · 기획서 작성

docs/design/idea_scope.md 를 근거로 이 제품의 기획서를 작성해줘.
아래 목차를 모두 채워 docs/design/02_기획서.md 로 저장해줘.
 1) 배경·목적   2) 대상·사용자   3) 범위(할 것/안 할 것)
 4) 핵심 개념·용어   5) 시스템 구성 개요   6) 마일스톤   7) 가정·제약
맨 위 메타 표와 맨 아래 변경이력 표도 넣고, 비전공자도 이해되게 써줘.

기대 산출물 docs/design/02_기획서.md 점검 포인트 7개 목차가 다 채워졌는가 / "할 것"과 "안 할 것"이 나뉘었는가

Part 2 · 기능명세서 (03)

기능명세서란?

무엇 "무슨 기능이, 무엇을 입력받아, 어떻게 처리해서, 무엇을 내놓는지" 하나하나 적은 문서. 각 기능에 FR-01 같은 번호를 붙여 나중에 추적합니다.

필수 목차 기능 목록(FR 번호) / 기능 상세(입력·처리·출력·예외) / 비기능 요구(NFR·SLO) / API 요약(§5) / 데이터 요약(§6)

P2 · 기능명세서 작성

docs/design/02_기획서.md 를 근거로 기능명세서를 작성해줘.
docs/design/03_기능명세서.md 에 아래대로 저장해줘.
 1) 기능 목록 - 각 기능에 FR-01 같은 번호를 붙여줘
 2) 기능 상세 - 기능마다 입력·처리·출력·예외 상황
 3) 비기능 요구(NFR) - 속도·보안·사용성 등 목표치(SLO)
 4) "API 요약", "데이터 요약" 은 제목만 잡아둬(뒤에서 채움)
쉬운 말로 쓰고, 메타·변경이력 표를 넣어줘.

기대 산출물 docs/design/03_기능명세서.md 점검 포인트 모든 기능에 FR 번호가 붙었는가 / 예외 상황이 적혔는가

Part 3 · 화면 설계서 (04) + UI 디자인시스템·IA (05)

화면 설계서란?

무엇 어떤 화면들이 있고, 각 화면이 무엇을 보여주고, 어떤 버튼·입력이 있으며, 화면 사이를 어떻게 이동하는지 그린 문서. 각 화면에 S-01 같은 번호를 붙입니다.

목업이란? 왜 지금 만드나

무엇 화면 설계서(04)·UI(05)를 실제로 클릭되는 화면 시안(HTML)으로 만들어 보는 것. 문서로만 상상하던 화면을 눈으로 확인하고 고칩니다.

왜 지금 내부 구조(데이터·API)를 만들기 전에 "보이는 모습"을 먼저 확정하면 나중에 갈아엎는 일이 줄어듭니다. 그리고 목업에서 바뀐 내용은 반드시 문서에 되맞춰야(역정합) 문서와 화면이 어긋나지 않습니다.

★ 검토 게이트 - 직접 확인하고 넘어가기

목업은 자동으로 "완성"되지 않습니다. 여러분이 직접 눈으로 보고 "이제 됐다"고 판단하는 관문이 바로 여기입니다. 이 게이트를 통과해야 다음 단계(역정합)로 넘어갑니다.

  • 화면이 만족스러울 때까지 앞의 수정 카드(P4-3)를 반복합니다. 게이트를 서둘러 지나치지 마세요.
  • 수정 요청은 정해진 문구를 그대로 붙여넣는 것이 아닙니다. 각자 자기 화면을 직접 보고, 자기가 발견한 문제를 자기 말로 구체적으로 적어야 합니다 - 아이디어도 화면도 사람마다 다르므로, 고칠 점과 프롬프트도 사람마다 달라야 합니다.
  • 이 관문을 건너뛰고 역정합하면, 아직 덜 다듬어진 화면이 그대로 문서에 굳어집니다.

데이터 모델(ERD)이란?
